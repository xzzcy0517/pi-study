# 第 1 讲 · 开头两行（shebang 与严格模式）

📍 **位置**：`pi/pi-test.sh` 第 1–2 行

```bash
#!/usr/bin/env bash
set -euo pipefail
```

---

## 🤔 这两行是干什么的？

**第 1 行**是写给**电脑**看的「说明书」：「这个文件请用 bash 这个程序来运行」。

你平时双击打开一个 `.txt` 文件，电脑知道用「文本编辑」打开；`.sh` 文件电脑不知道用什么打开，所以文件自己要在第一行写明。这一行有个专门的名字叫 **shebang**（读作「夏棒」），特征就是 `#!` 开头。

**第 2 行**是写给**脚本自己**的「纪律要求」，叫「严格模式」。shell 脚本默认很懒散：出错了也继续跑、变量没定义就当空气。这行代码一开头就立了三条规矩：

| 规矩 | 大白话 |
|---|---|
| `-e` | 哪一步出错了，**立刻停下**，别硬着头皮往下跑 |
| `-u` | 用了**没定义过**的变量，直接报错（防止打错字被当成空值） |
| `pipefail` | 一条流水线（用 `\|` 连接的命令）里**任何一环**出错都算出错 |

为什么要这么严格？因为这是一个「启动器」脚本——它要是带病运行，会把 Pi 启动成一个坏状态，你还不知道哪里出的问题。宁肯当场停下，也不带病上岗。

---

## 🧪 动手跑

把下面**整块**复制到终端里跑（实验文件会建在 `c-pi/labs/r1-strict/` 里）：

```bash
mkdir -p /Users/admin/Desktop/pi-study/c-pi/labs/r1-strict
cd /Users/admin/Desktop/pi-study/c-pi/labs/r1-strict

# 实验 1：第 1 行的作用 —— 声明“用 bash 运行我”
cat > hello.sh <<'EOF'
#!/usr/bin/env bash
echo "你好，我是用 bash 运行的"
EOF
chmod +x hello.sh
./hello.sh
```

**预期输出**：

```text
你好，我是用 bash 运行的
```

```bash
# 实验 2：纪律 -e —— 出错的命令后面，还跑不跑？
printf 'echo "第 1 步"\nfalse\necho "第 2 步（失败了却还在跑）"\n' > strict-off.sh
printf 'set -e\necho "第 1 步"\nfalse\necho "第 2 步（执行不到）"\n' > strict-on.sh

echo "--- 没有纪律的脚本 ---"
bash strict-off.sh; echo "  退出码 $?"

echo "--- 有纪律的脚本 ---"
bash strict-on.sh; echo "  退出码 $?"
```

**预期输出**：

```text
--- 没有纪律的脚本 ---
第 1 步
第 2 步（失败了却还在跑）
  退出码 0
--- 有纪律的脚本 ---
第 1 步
  退出码 1
```

看到了吗：`false` 是一个「注定失败」的命令（用来假装出错）。没有纪律时，第 2 步照样跑，还假装一切正常（退出码 0）；有纪律时，脚本在出错处**当场停下**，退出码变成 1。

```bash
# 实验 3：纪律 -u —— 没定义过的变量，能不能用？
printf 'echo "未定义的值是：[${WHO}]"\n' > u-off.sh
printf 'set -u\necho "未定义的值是：[${WHO}]"\n' > u-on.sh

bash u-off.sh; echo "  退出码 $?"
bash u-on.sh 2>&1; echo "  退出码 $?"
```

> 💡 **`2>&1` 是什么？** 每个程序有两个「出口」：
>
> | 出口 | 名字 | 走什么东西 |
> |---|---|---|
> | **1 号** | 正常输出 | 程序正常运行的结果 |
> | **2 号** | 错误输出 | 报错、警告 |
>
> 平时在终端里，两个出口都打印到屏幕，所以你分不出来。但一旦输出被**接管**（存进文件 `>`、传给另一条命令 `|`），默认只有 1 号出口被接管，2 号错误还会冲到屏幕上（或干脆丢掉）。
>
> `2>&1` 的意思就是：**把 2 号出口接到 1 号出口上**——「>&」是接管道的符号，让错误信息跟着正常输出走同一条道。上面实验里加它，是为了让报错和正常输出呆在一起，和教程里的预期输出逐行对应。试试下面这组对比就懂了：

```bash
# 只看效果：把输出存进文件，错误会怎样？
ls /不存在的路径 > out1.txt                      # 只接管 1 号出口
echo "（错误冲到了屏幕上，out1.txt 里是：[$(cat out1.txt)]）"

ls /不存在的路径 > out2.txt 2>&1                 # 2 号也并进来
echo "（屏幕安静了，out2.txt 里是：[$(cat out2.txt)]）"
rm -f out1.txt out2.txt
```

**预期输出**：

```text
ls: /不存在的路径: No such file or directory
（错误冲到了屏幕上，out1.txt 里是：[]）
（屏幕安静了，out2.txt 里是：[ls: /不存在的路径: No such file or directory]）
```

第一次：错误没进文件，文件是空的；第二次：`2>&1` 把错误一并逮进文件，屏幕干干净净。

```bash
# 实验 4：纪律 pipefail —— 流水线里一环出错算不算错？
( false | true; echo "不开 pipefail：退出码 $?" )
( set -o pipefail; false | true; echo "开了 pipefail：退出码 $?" )
```

**预期输出**：

```text
未定义的值是：[]
  退出码 0
u-on.sh: line 2: WHO: unbound variable
  退出码 1
不开 pipefail：退出码 0
开了 pipefail：退出码 1
```

- `-u` 的效果：没纪律时，不存在的 `WHO` 被当成空串（`[]`），**拼错字也无声无息**；有纪律时直接报 `unbound variable`。
- `pipefail` 的效果：`false | true` 这条流水线，**最后**一环 `true` 是成功的，所以默认算成功（退出码 0）——但第一环明明失败了！开了 `pipefail`，整条流水线才算失败（退出码 1）。

---

## ✅ 小结

第 1 行告诉电脑「用 bash 运行我」；第 2 行给脚本立下「出错就停、不许用没定义的变量、流水线出错要认账」三条纪律。后面的每一行，都在这三条纪律的约束下执行。
